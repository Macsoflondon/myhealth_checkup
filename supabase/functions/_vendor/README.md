# Vendored runtime files

## lovable-mcp-js-0.26.3

The runtime half of `@lovable.dev/mcp-js@0.26.3` (MIT, see `LICENSE`): `dist/index.js`,
`dist/stacks/supabase/index.js` and the chunks they import. The files are byte-identical
to the published npm tarball. Nothing is edited.

### Why

`mcp` and `mcp-public` are regenerated by the `mcp-js` Vite plugin and import
`npm:@lovable.dev/mcp-js@0.26.3`. That package lists `esbuild` as a dependency and `vite`
as a peer, both for its build-time plugin. When a deploy resolves the npm package, it
installs both, and `vite` pulls in rolldown and lightningcss with glibc and musl native
binaries. Each function bundled to about 100 MB (93 MB of npm packages), and every
function deploy, on Supabase Preview branches and from `main`, failed with
`413 request entity too large` from 9 October 2026.

An earlier fix linked `esbuild` and `vite` to empty stubs through `links` in `deno.json`.
Deno honours that locally, but Supabase's deploy did not, and the 413 remained.

`supabase/functions/deno.json` now maps the two `mcp-js` specifiers to these files through
`imports`, which Supabase's deploy has always honoured. The npm package is never resolved,
so esbuild and vite are never installed. `mcp` resolves 20 MB of npm packages instead of
93 MB. Its runtime dependencies are mapped to the versions the package declares:
`@modelcontextprotocol/sdk` 1.28.0 (pinned by the package) and `jose` 6.2.13 (within its
`^6.2.2`). `zod` stays the functions' own import, as the package treats it as a peer.

Verified on 28 October 2026: `initialize` and `tools/list` responses are byte-identical
before and after, for `mcp-public` (200, same tool list) and `mcp` (401 without a token),
and all 74 functions resolve their module graph with no errors.

### When the Vite plugin upgrades mcp-js

If regenerated `mcp` files import a new version, `src/lib/ci/__tests__/edge-mcp-vendor.test.ts`
fails. Then:

1. `npm pack @lovable.dev/mcp-js@<version>` and copy `dist/index.js`,
   `dist/stacks/supabase/index.js`, every chunk they import, and `LICENSE` into
   `_vendor/lovable-mcp-js-<version>/`.
2. Point both `npm:@lovable.dev/mcp-js@<version>` keys in `deno.json` at the new files, and
   update the `@modelcontextprotocol/sdk` and `jose` versions to the new package's
   declared dependencies.
3. Confirm no vendored file imports `esbuild` or `vite`, then delete the old version's folder.
