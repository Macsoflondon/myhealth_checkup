# Empty npm stand-ins for edge function bundles

`supabase/functions/deno.json` links the npm packages `esbuild` and `vite` to the
empty packages in this folder.

## Why

The `mcp` and `mcp-public` functions are generated by the `@lovable.dev/mcp-js`
Vite plugin and import `npm:@lovable.dev/mcp-js`. That package lists `esbuild` as
a dependency and `vite` as a peer dependency, because its Vite plugin and CLI use
them at build time. Deno installs both for the edge function, and `vite` pulls in
rolldown and lightningcss. Deno installs the native binaries for both glibc and
musl, so each of the two functions bundled to about 100 MB.

Supabase rejected that upload with
`unexpected update function status 413: {"message":"request entity too large"}`.
Every Supabase Preview branch failed on it from 9 October 2026, and so did
function deploys from `main` (the `main` branch reported `FUNCTIONS_FAILED`).

The runtime entry of `@lovable.dev/mcp-js` (`dist/index.js` and the chunks it
imports) never imports `esbuild` or `vite`. Only `dist/stacks/*/vite.js` and
`dist/cli/` do, and edge functions do not load those files.

With the links in place, `mcp` bundles to about 24 MB. Its responses to
`initialize` and `tools/list` are byte-identical to the unlinked build, for both
`mcp` and `mcp-public` (checked on 28 October 2026 with Deno 2.9).

## Rules

- Each stub throws if anything imports it, so an unexpected runtime use fails
  loudly instead of silently.
- A linked package must satisfy the version range that depends on it.
  `@lovable.dev/mcp-js` 0.26.3 needs `esbuild` `^0.27.0` and `vite`
  `>=5.0.0 <9.0.0`. If an upgrade changes those ranges, update the `version`
  fields here, or Deno falls back to the real packages and the 413 returns.
- The folder name starts with `_`, so Supabase does not treat it as a function.
