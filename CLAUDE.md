# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A TanStack Start (React 19, SSR, file-based routing) health-test/blood-test comparison platform — myhealth checkup — originally scaffolded by [Lovable](https://lovable.dev/projects/37e227e1-0d67-4515-b064-99c243036534) (pushes to this repo sync back to the Lovable project). It compares prices, biomarkers and clinics across UK private test providers (Medichecks, Randox Health, Goodbody Clinic, Lola Health, London Medical Laboratory, London Health Company, Clinilabs, Medical Diagnosis), backed by a scraper pipeline, an admin panel for managing scraped data, a Super-Admin portal ("Crux Control"), and AI-assisted test analysis/recommendations (the "Human Context Engine"). Supabase (project id `clvuioagsgfadynuvodj`) is the backend for everything — database, auth, edge functions, cron, vault.

The package is still named `vite_react_shadcn_ts` in `package.json` — a leftover from the original Lovable scaffold, harmless but worth knowing so it isn't mistaken for a second project.

**Note for future sessions:** a companion project doc, the Crux Master Specification, is the up-to-date narrative account of what each of the platform's five core systems (Crux Dataset, TEC Engine, Human Context Engine, Automated Infrastructure, Crux Control) actually does today versus what it's meant to do. Read it before making architectural claims about those systems — it is corrected and re-dated as things change, this file is not.

## Commands

- `npm run dev` — `vite dev` (TanStack Start dev server; Playwright's default `baseURL` assumes it serves on `localhost:8080`)
- `npm run build` / `npm run build:dev` — `vite build` (production / development-mode)
- `npm run prebuild` — chained pre-build gate: `scripts/check-secrets.sh` → `scripts/check-rls-grants.mjs` → `scripts/generate-sitemap.ts` → `scripts/seo-regression.mjs`. Runs automatically before `build` via npm's lifecycle hook; do not skip it when diagnosing a build that "works locally" but fails in CI.
- `npm run lint` — ESLint (flat config in `eslint.config.js`)
- `npm run format` — Prettier, writes in place
- `npm test` — Vitest, watch mode by default (jsdom, globals on). Tests live alongside source as `src/**/*.{test,spec}.{ts,tsx}`.
- `npm run test:smoke` — `playwright test tests/e2e/render-smoke.spec.ts --project=chromium-desktop --workers=2`. There **is** a committed `playwright.config.ts` (testDir `./tests/e2e`, two projects: `chromium-desktop` and `chromium-mobile`, trace `retain-on-failure`) — this supersedes any earlier note that no Playwright config existed.
- `npm run security:check` — `scripts/check-secrets.sh` + `scripts/check-rls-grants.mjs` on their own, outside the full prebuild chain
- `npm run seo:check` / `npm run seo:structured-data` / `npm run sitemap` — SEO regression, structured-data validation, and sitemap generation scripts, individually
- `npm run audit:biomarker-references` — `scripts/audit-biomarker-references.mjs`
- `npm run preview` — preview a production build
- Supabase edge function tests (e.g. `supabase/functions/*/index.test.ts`, where present) are **Deno tests**, not part of `npm test` — they need `deno test` with network/env access against a running (local or deployed) function.

No `.env` is required to run the app: `src/integrations/supabase/client.ts` is a Lovable-generated file that hardcodes the Supabase project URL and the public/anon (publishable) key directly in source — this is standard for a Supabase anon key (it's meant to be public) and not a leak. Any earlier note about `VITE_SUPABASE_URL`/`VITE_SUPABASE_KEY` env vars gating local dev is stale; those aren't read anywhere in the current client setup. Path alias `@/*` → `src/*` (see `tsconfig.json`, mirrored in `components.json` for shadcn).

## Architecture

**Stack:** React 19.2, TanStack Router 1.170 + TanStack Start 1.168 (file-based routing, SSR via Nitro — `nitro@3.0.260603-beta` is a devDependency), Tailwind CSS v4 via `@tailwindcss/vite` (not a `tailwind.config.js`-driven v3 setup), Vite 8 as the underlying build tool. This is **not** a plain Vite+React SPA with `react-router-dom`/`BrowserRouter` — there is no `react-router-dom` dependency at all. If you find documentation (including older versions of this file) describing `authRoutes`/`contentRoutes`/`featureRoutes` route-module composition under `BrowserRouter` in an `App.tsx`, that describes a pre-TanStack-Start version of this codebase and no longer matches what's deployed.

**Data layer (bottom to top):** `src/integrations/supabase/client.ts` (raw Supabase client + generated `types.ts`) → `src/api/supabase` (API-level wrappers) → `src/services/*` (business logic — `ProviderDataService`, `LiveDataService`, `CompareService`, `CacheService`, `EncryptionService`, `UserPreferencesService`, with `queryBuilders/` and `transformers/` subfolders) → consumed by pages/components through `@tanstack/react-query`. The `QueryClient` is now created in `src/router.tsx` (not `App.tsx`) and passed into `createRouter({ context: { queryClient }, scrollRestoration: true, defaultPreloadStaleTime: 0 })`; its defaults are `staleTime: 10 min, gcTime: 30 min, retry: 1, refetchOnWindowFocus: false`.

**Routing:** real TanStack Start file-based routing under `src/routes/`, auto-generating `src/routeTree.gen.ts` (do not hand-edit that file). The convention is flat files with dot-separated segments rather than nested folders — e.g. `src/routes/admin.recovery.tsx` → `/admin/recovery`, `src/routes/medichecks.$testId.tsx` → `/medichecks/:testId`. `src/routes/__root.tsx` is the actual document root: it renders real `<html>/<head>/<body>` via TanStack Start's `<HeadContent/>`/`<Scripts/>`, and composes `AuthProvider` → `SessionSecurityProvider` → `QueryClientProvider` → `I18nextProvider` → `HelmetProvider` → `TooltipProvider` around the page, plus `GlobalHreflang`, `FloatingNavDock`, `AutoTranslatePage`, `GlobalComparisonBar`, and an error boundary around `<Outlet/>`. It also carries the site's static medical-review disclaimer and the JSON-LD Organization/WebSite schema.

Route inventory highlights (not exhaustive — see `routeTree.gen.ts` for the full list):
- Flat marketing/content/tool pages at the root (`/compare`, `/biomarkers`, `/faqs`, `/quiz`, `/hidden-gap-detector`, `/how-we-rank`, etc.) plus locale-agnostic legal/compliance pages (`/privacy-policy`, `/terms`, `/modern-slavery`, `/fair-trading`, …).
- An **admin cluster** at `/admin/*` (19 routes: `alert-routing`, `audit-console`, `biomarker-audit`, `biomarker-validation`, `change-log`, `clinical-safety`, `data-refresh`, `data-sharing`, `encryption-status`, `login`, `ops`, `performance`, `recovery`, `scrapers`, `security-diff`, `seo-status`, `soc-watch`, `test-dashboard`, `test-mapper`, `test-upload`) — this drives the scraper/data-ingestion pipeline and platform operations.
- **Crux Control**, the Super-Admin portal, at `control.index.tsx` / `control.$section.tsx` (`/control`, `/control/:section`) — distinct from the `/admin/*` cluster above.
- Per-provider directories for all 8 active providers, each with an index and a `$testId` page (e.g. `medichecks.index.tsx` + `medichecks.$testId.tsx`), plus a separate `providers.<provider>.tsx` single profile page per provider (e.g. `/providers/medichecks`). A newer, more general `provider.$providerId.index.tsx` / `provider.$providerId.tests.index.tsx` / `provider.$providerId.tests.$testId.tsx` family also exists alongside these — it looks like the intended consolidation target for the 8 hardcoded per-provider route sets, not yet completed. Two route files look like uncleaned legacy duplicates worth checking before extending provider routing further: `goodbody.$testId.tsx` alongside `goodbody-clinic.$testId.tsx`, and `randox-health.$testId.tsx` alongside `randox.$testId.tsx`.
- `src/routes/api/public/` holds TanStack Start **server routes** (e.g. `blog-aggregate`, `diagnostics.aborts`) — these are part of the frontend app, not Supabase edge functions, despite the similar-sounding name.
- `src/routes/[.]lovable.oauth.consent.tsx` is a Lovable-platform-internal route; leave it alone.

**Auth & security:** `AuthContext` (`src/context/AuthContext.tsx`) + `SessionSecurityProvider` wrap the app via `__root.tsx`; `EncryptionService` handles sensitive data. Admin pages have a separate `AdminAuth` flow. `admin-recovery` (Supabase edge function) issues/redeems break-glass recovery tokens for admin accounts and enforces AAL2 (MFA) on issuance.

**i18n & SEO:** `src/i18n/config.ts` + 11 locale files under `src/locales/` (en, es, fr, de, it, pt, nl, pl, ar, zh, ja); `GlobalHreflang` component emits matching hreflang tags. This is a content/SEO-heavy site — treat locale and hreflang consistency as a first-class concern when touching routing or page metadata. `scripts/generate-sitemap.ts` and `scripts/seo-regression.mjs`/`scripts/validate-structured-data.mjs` run as part of `prebuild`/`seo:check`.

**Deployment: Cloudflare Pages, not Vercel.** `.github/workflows/deploy.yml` triggers on push to `main` (plus manual `workflow_dispatch`), runs `npm run build`, and publishes `dist/` via `cloudflare/pages-action@v1` using three GitHub secrets (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_PROJECT_NAME`). This resolves what earlier versions of this file flagged as ambiguous. `vercel.json` still exists in the repo (caching + security headers, CSP) but nothing in CI references Vercel — treat it as vestigial unless you find evidence otherwise, and don't assume its headers are actually being served. **Known live issue (as of 2026-09-04):** the production domain was found returning 404 on both `/` and known static assets during a routine deploy check, despite `deploy.yml` being correctly configured — root cause not yet confirmed (needs direct Cloudflare dashboard access: check whether the Pages project is receiving deploys, whether DNS/custom-domain binding to the GitHub-connected project is intact, and recent deploy logs). Don't assume production is serving current code without checking.

**Bot-aware prerendering (see `PRERENDER.md`):** plain CSR returns an empty shell that most non-Googlebot AI crawlers can't render. `functions/_middleware.ts` (a Cloudflare Pages Function, rooted at `functions/`, separate from `supabase/functions/`) inspects the User-Agent: humans always get the SPA shell; recognized bots get a prerendered static snapshot (built by `scripts/prerender-routes.mjs`, ~60 routes) if one exists at `dist/<route>/index.html`, else fall back to the SPA shell. `functions/_known-routes.ts` backs this. This only makes sense given Cloudflare Pages is confirmed as the real deploy target above.

**Backend (`supabase/functions/`):** organized by responsibility — AI/analysis (`ai-human-context`, the single canonical AI recommendation engine — see below; `blood-test-analysis`, `ai-test-mapper`, `quiz-recommendations`), provider scrapers (`*-scraper` per provider, e.g. `medichecks-scraper`, `randox-scraper`, plus orchestrators `run-all-scrapers`/`scrape-all-clinics`), admin/security (`admin-recovery`, `verify-admin-mfa`, `encrypt-sensitive-data`, `check-leaked-password-protection`), and notifications/marketing (`send-test-notification`, `newsletter-subscribe`, `price-alert-checker`). Several ship their own `index.test.ts` (Deno tests, see Commands above). Cron-triggered functions are invoked through vault-backed SQL helpers (`call_edge_with_service_role`, `call_edge_with_automations`) rather than plaintext secrets in `cron.job` commands — follow that pattern for any new scheduled edge-function call rather than embedding a key in the job definition.

**The Human Context Engine (`ai-human-context`):** takes a free-text wellness query plus optional age/gender/method preference, scores active priced tests via hand-built keyword groups (fatigue→thyroid/iron, heart→cholesterol, etc.) plus popularity/price/gender heuristics, and hands the top 30 to GPT-4o-mini for a validated, schema-checked recommendation — falling back to the scoring-only result if the AI call fails or doesn't validate. As of 2026-09-04 it also calls OpenAI's embeddings endpoint directly (`text-embedding-3-small`, 1536-dim, matching `biomarker_hub.embedding`'s column type) and the pre-existing `match_biomarkers` RPC (an HNSW-indexed pgvector search over `biomarker_hub`, built 29 August but unused until now) to find biomarkers semantically related to the query, then folds matches into both the scoring pass and the GPT prompt. Both the embeddings call and the RPC are wrapped to fail closed to empty — if either errors, scoring/recommendation proceeds exactly as it did before this wiring existed.

**Known issue blocking full AI recommendations (as of 2026-09-04): `OPENAI_API_KEY` (the edge function secret, not a Vault entry) is invalid.** Every `ai-human-context` request since 2026-07-23 (confirmed via `ai_operation_logs`, `job_type = 'ai-human-context'`, `error_type = 'ai_fallback_used'`) has failed its GPT-4o-mini call with "Incorrect API key provided: sk-emerg…d89C" and silently served the non-AI scoring fallback instead — the failure is graceful (users still get results) so nothing looked broken externally, but no real GPT-4o-mini analysis, and no benefit from the new semantic-biomarker wiring either (it shares the same key), has actually reached users for at least 6 weeks. This needs a valid key set in the Supabase project's edge function secrets — not something fixable from a migration or code change.

**UI:** shadcn-ui components in `src/components/ui` (config: `components.json`, Tailwind base color `slate`, no RSC). Other component folders are domain-organized: `admin`, `auth`, `booking`, `clinic`, `compare`, `providers`, `tests`, `dashboard`, `search`, `security`, `seo`, `reviews`, `ai`.

**Pricing display / the TEC Engine:** `provider_tests` has both `price` (raw scraped price) and `total_expected_cost` (intended to roll up phlebotomy/GP-review add-ons into one comparable figure). As of 2026-09-04, confirmed by reading `src/pages/TestDetailPage.tsx` and `src/components/compare/TestProviderPriceTable.tsx` directly: **the live UI reads `price`, never `total_expected_cost`.** Separately, `total_expected_cost` is populated for 721/737 active rows but is bit-for-bit identical to `price` on 701 of those — it differs (by an average of ~£1) on only 20 rows platform-wide. So even once wired up, most tests won't visibly change; the real gap is that phlebotomy/GP-review add-on costs mostly aren't being captured into `total_expected_cost` in the first place. Don't assume "Total Expected Cost" language anywhere in the product reflects what's on screen today.

## Writing site content

Apply the `stop-slop` skill to all prose written for the site: page copy, headings, meta titles and descriptions, locale strings under `src/locales/`, marketing email and newsletter copy, and any user-facing text in components.

This applies to content only. Do not apply it to conversation with the user, commit messages, PR descriptions, or code comments.
